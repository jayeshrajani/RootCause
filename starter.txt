# GitHub Copilot Master Prompt: RootCause

You are the lead software architect and senior full-stack engineer for **RootCause**, an AI-powered crop distress triage and early-warning platform being built for the **Google AI Builder Cup 2026**, under Sustainability & Social Impact.

We are a two-developer team, Jayesh and Shivansh.

Your task is to establish a clean, production-minded, extensible monorepo that we can develop collaboratively on GitHub.

**Important: Begin with a functional skeleton. Do not implement the entire product in one pass.** Build incrementally, preserve modularity, and create clear integration points for upcoming functionality.

## 1. Product Vision

RootCause is NOT another crop disease detection app.

Our goal is to help farmers understand:

- What could be wrong with their crop?
- How urgent is the situation?
- What evidence supports the diagnosis?
- What additional information would improve certainty?
- What safe next steps should they take?

The system will eventually combine crop photographs, farmer-reported symptoms, weather data, satellite vegetation indicators, and trusted agricultural knowledge.

The application must distinguish observed facts, hypotheses, missing evidence, and recommendations. Never present AI guesses as confirmed diagnoses.

## 4. Milestone 0: Repository Skeleton

This is the **only milestone to implement initially**.

Create a working Next.js frontend and FastAPI backend.

### Frontend

Implement:

1. RootCause landing page
2. Reusable application layout
3. Farmer report form
4. Crop selection
5. Photo selection supporting 1–3 images
6. Text description
7. Approximate location fields
8. Optional symptom duration
9. Submit button
10. Triage results page using clearly labeled mock data

The UI should feel like a practical agricultural decision-support tool, not a generic AI chatbot.

Use clear visual hierarchy, accessible components, helpful empty states, loading states, and error messages.

### Backend

Implement:

- `GET /api/v1/health`
- `POST /api/v1/triage`

The triage endpoint must accept multipart form data with image uploads and field information.

Validate image count, file type, file size, required fields, and geographic coordinates.

Initially return deterministic mock triage results. Mock responses must be explicitly identifiable as mocks.

### Triage Response Contract

Create a reusable typed response contract containing:

```text
report_id
status
crop
summary
urgency
urgency_reason
possible_causes[]
evidence[]
missing_information[]
recommended_actions[]
requires_expert_review
generated_at
data_sources[]
```

Each possible cause should include its name, explanation, supporting evidence, contradictory evidence, and an indication of uncertainty.

Evidence should specify its source, availability, observation, and relevant timestamp where appropriate.

Recommended actions should include a priority and indicate when expert verification is needed.

Never fabricate weather, satellite observations, or agricultural citations.

### Frontend/Backend Integration

- Implement an API client in the frontend.
- Connect the report form to FastAPI.
- Render the response using reusable results components.
- Keep the form and result schemas aligned.
- Provide actionable errors when the backend is unavailable.
- Configure CORS for local development.

The application must work end-to-end without a Gemini API key.

## 5. Milestone 1: Gemini Integration

Do NOT implement until Milestone 0 is complete and verified.

Later, introduce a Gemini integration service that:

- Accepts crop imagery and farmer symptoms
- Produces a structured triage assessment
- Validates model output through Pydantic
- Handles malformed output, timeouts, and API errors
- Separates model hypotheses from verified external evidence
- Avoids unsupported certainty
- Returns an explicit analysis mode and provenance

Keep model configuration separate from route handlers.

## 6. Milestone 2: Weather Intelligence

Integrate Open-Meteo using approximate field coordinates.

Retrieve relevant recent weather signals, such as rainfall, temperature, and humidity.

Generate weather-based observations independently of Gemini and pass them to the triage orchestrator.

Unavailable weather information must not be interpreted as normal weather.

Use actual observation periods and timestamps.

## 7. Milestone 3: Satellite Intelligence

Design a satellite adapter supporting:

- Field geometry or approximate coordinates
- Vegetation indicators such as NDVI
- Historical comparisons
- Cloud-cover limitations
- Temporal changes
- Source metadata

Do not claim reliable field-specific conclusions from a single approximate coordinate without validating spatial resolution and field boundaries.

Make satellite evidence optional.

## 8. Milestone 4: Knowledge-Grounded Triage

Introduce agricultural knowledge retrieval from credible, attributable sources.

The system should connect potential crop issues to relevant agricultural guidance.

Separate retrieved statements from the model's interpretations.

Do not invent citations or recommend specific chemical treatment doses without reliable local guidance.
